系统设计面试中的 API 设计指南简报

本简报旨在系统梳理系统设计面试中 API 设计的核心原则、协议选择、常用设计模式及安全规范。API 设计是系统设计面试中“交付框架”（Delivery Framework）的关键环节，主要用于定义客户端与系统之间的交互方式。

执行摘要

在系统设计面试中，API 设计通常占用约 5 分钟的时间。大多数面试官并不要求 API 设计达致完美，而是希望看到候选人具备合理的 API 设计能力，并能迅速过渡到更复杂的分布式系统架构探讨中。然而，对于前端、产品角色、初级岗位或特定注重 API 的公司（例如 Scale AI、Atlassian），API 设计可能会被深入追问。

高质量的 API 设计遵循高度可预测的模式：选择合适的协议、清晰定义资源、规范数据输入输出格式，并结合幂等性与安全性保障。在没有特殊需求的情况下，应默认选择 REST 协议；而在内部微服务高性能通信或复杂客户端多变查询场景下，则可灵活选用 RPC (gRPC) 或 GraphQL。

核心主题详细分析

1. API 协议选择与适用场景

面试中通常涉及三种主要的 API 通信协议：

协议类型 核心机制与特点 最佳适用场景 关键考量 / 权衡
REST 基于标准 HTTP 方法（GET, POST, PUT, DELETE），围绕 URL 标识的资源进行操作。 Web 和移动应用的标准 CRUD 操作、公共 API（默认首选）。 简单易用，工具生态成熟，适合 90% 的场景。
GraphQL 单一端点，使用查询语言（Query Language），由客户端精确指定所需的数据字段。 多端差异化需求（如移动端需要精简数据，Web 端需要详细分析数据），避免数据“过度获取”（Over-fetching）或“获取不足”（Under-fetching）。 增加系统复杂度（需解析查询、校验 Schema）；存在 N+1 查询问题（需使用 Dataloader/批处理解决）；需字段级权限控制。
RPC / gRPC 以“动作/过程”为中心（如 checkPermission），采用二进制序列化（Protocol Buffers）与 HTTP/2 传输。 内部微服务间通信、高性能要求场景、多语言（Polyglot）环境、需要双向流传输的场景。 效率远高于 JSON-over-HTTP；提供编译时类型安全。注：Apache Thrift 也是一种常见的 RPC 框架。

注：对于通知、聊天或实时更新等实时功能，应选用 WebSockets 或服务器发送事件（SSE）等持久连接协议，而非传统 API。

2. REST 资源建模与 HTTP 语义

(1) 资源建模（Resource Modeling）

REST 的核心是将系统中的**实体（Entities）**建模为资源。

  • 命名规范：资源必须使用复数名词表示“事物”（Things），而非“动作”（Actions）。例如：使用 /events 和 /bookings，而非 /getEvents 或 /createBooking。

  • 资源层级与关系：

    • 路径参数（Path Parameters）：用于表示必填的父子关系或特定资源标识（例如：/events/{id}/tickets 或 /events/123）。
    • 查询参数（Query Parameters）：用于表示可选的筛选、排序或分页条件（例如：/tickets?event_id=123&section=VIP）。

  • Ticketmaster 示例 API 设计：*

GET  /events                    # 获取所有活动列表
GET  /events/{id}               # 获取特定活动详情
GET  /venues/{id}               # 获取特定场馆详情
GET  /events/{id}/tickets       # 获取某活动的可用门票
POST /events/{id}/bookings     # 为某活动创建新订购
GET  /bookings/{id}             # 获取特定订购详情

(2) HTTP 方法与幂等性（Idempotency）

幂等性指多次重复执行同一请求，系统最终状态是否保持一致。

+--------+------------------------------------+--------+--------+
| HTTP方法| 功能说明                            | 安全性 | 幂等性 |
+--------+------------------------------------+--------+--------+
| GET    | 获取数据，不改变服务器状态           | 是     | 是     |
| POST   | 创建新资源，由服务器分配 ID          | 否     | 否     |
| PUT    | 替换整个资源；若不存在则创建         | 否     | 是     |
| PATCH  | 局部更新资源                       | 否     | 不保证 |
| DELETE | 删除资源                           | 否     | 是     |
+--------+------------------------------------+--------+--------+
  • GET：仅读取，多次调用结果一致。
  • POST：非幂等，网络重试可能导致重复创建（如重复下单）。
  • PUT：幂等，使用相同数据多次覆盖，最终状态相同。
  • PATCH：不保证幂等（如“把邮箱修改为 X”是幂等的，但“追加列表元素”是非幂等的）。
  • DELETE：幂等，首次删除返回 204 No Content，后续重复调用可能返回 404 Not Found，但服务器最终资源被删除的状态不变。

(3) 传递数据与返回格式

  • 数据输入：
    • Path Parameters：结构化标识，决定访问哪个端点。
    • Query Parameters：修饰符，改变端点行为（第一项用 ?，后续用 & 连接）。
    • Request Body：复杂 payload，适合传输敏感或大量数据（如 JSON 结构）。
  • 数据返回：由状态码与响应体（通常为 JSON）组成。
    • 常见状态码分类：200（成功）、201（已创建）、400（客户端请求错误）、401（需要身份验证）、404（资源未找到）、500（服务器错误）。面试中重点在于区分客户端错误（4xx）与服务器错误（5xx）。

3. API 设计九大核心原则

  1. 围绕资源而非动作设计：暴露系统中的实体，用 HTTP 方法表达具体操作。
  2. 全局保持一致性：统一命名约定、参数名称及响应格式（例如统一使用 status，避免混用 state）。
  3. 遵循最小惊奇原则（Principle of Least Surprise）：严格遵循 HTTP 语义（如 GET 不修改数据，200 即代表成功，不可在 200 响应体中返回 "success": false）。
  4. 保持 API 无状态（Stateless）：每个请求必须包含处理所需的全部信息（如 Auth Token、参数）。无状态便于水平扩展。
  5. 保证重试安全性：面对网络故障，设计幂等机制（如为 POST 请求引入幂等键）。
  6. 对所有可增长的集合进行分页：提供分页支持并设置单页数量上限限制（ limit cap），防止大查询压垮数据库。
  7. 默认启用安全防护：身份验证应为默认选项（公开端点需显式标记），并配合授权校验与速率限制。
  8. 无平滑平滑演进（避免破坏性变更）：新增字段是安全的，但重命名、删除或变更已有字段属于破坏性变更，需制定版本控制策略。
  9. 提供具可操作性的错误信息：使用正确的 HTTP 状态码，并在响应体中提供机器可读的代码与人类可读的信息。

4. 常见 API 模式

(1) 分页模式（Pagination）

  • 基于偏移量的分页（Offset-based）：
    • 语法：/events?offset=20&limit=10
    • 特点：简单直观，适用于大多数普通场景。
    • 缺点：在大数据集或数据频繁插入时，跳页会导致重复或遗漏数据。
  • 基于游标的分页（Cursor-based）：
    • 语法：/events?cursor=cmd9atj3p000007ky19w1dpy2&limit=10
    • 特点：游标是特定记录的编码引用（如 ID 或时间戳）。在实时数据或高并发场景下更稳定，但无法直接跳转到指定页码（如“跳至第 5 页”）。

(2) 幂等键（Idempotency Keys）

针对支付、订订等非幂等的 POST 操作，客户端在请求头中生成并发送唯一的 UUID：

POST /events/123/bookings
Idempotency-Key: 8e03978e-740c-4c2e-abd1-52f427d5c177

服务器会将该 Key 与首次处理结果一并存储。当携带相同 Key 的重试请求到达时，服务器直接返回已存储的响应，避免二次扣费或重复订票。

(3) 统一错误响应信封（Consistent Error Envelope）

通过统一的响应结构，方便客户端集中处理错误：

{
  "error": {
    "code": "SEAT_UNAVAILABLE",
    "message": "Section VIP has only 1 seat remaining"
  }
}

(4) 版本控制策略

  • URL 版本控制（推荐）：如 /v1/events 或 /v2/events。显示直观，路由处理简单，面试中优先使用。
  • Header 版本控制：如 Accept-Version: v2 或 API-Version: 2。保持 URL 干净，但不够直观。

5. 安全考量

(1) 认证（Authentication）与授权（Authorization）

  • 认证：确认请求者的身份（你是谁）。
  • 授权：确认该身份是否有权执行特定操作（你能做什么）。

(2) API Keys vs JWT Tokens

+----------------+----------------------------------------+----------------------------------------+
| 特性           | API Keys                               | JWT (JSON Web Tokens)                  |
+----------------+----------------------------------------+----------------------------------------+
| 机制           | 长期随机字符串，需服务器查库校验         | 自包含签名 Token，编入用户信息与过期时间|
| 状态存取       | 有状态（需数据库查找）                 | 无状态（基于密钥校验签名，无需查库）     |
| 最佳适用场景   | 服务间通信、第三方开发者 API 访问       | 用户会话管理（Web / 移动端应用）       |
+----------------+----------------------------------------+----------------------------------------+

(3) 基于角色的访问控制（RBAC）

系统将权限赋予角色，再将角色赋予用户。API 收到请求后需进行双重校验：

  1. 用户是否已通过身份验证（有效 JWT）？
  2. 用户是否有权操作此资源（如：普通用户只能取消自己的订单，管理员可操作所有订单）。

(4) 速率限制与节流（Rate Limiting & Throttling）

在 API 网关层或中间件实现，防止恶意刷接口或偶然超载。超限时返回 HTTP 429 Too Many Requests。

  • 按用户限制：如认证用户每小时 1000 次请求。
  • 按 IP 限制：如未认证请求每小时 100 次。
  • 按端点限制：如防抢票端点每分钟最多 10 次尝试。

重要引用与上下文

1. 关于默认协议选择： “Default to REST unless you have a specific reason not to. It's well-understood, has great tooling, and works for 90% of use cases.”

上下文：在面试中不要过度复杂化。除非遇到复杂的客户端多变数据提取需求（选 GraphQL）或内部微服务高性能通信（选 RPC），否则统一默认选用 REST。

2. 关于面试中的时间分配： “Do your best to not spend more than 5 minutes outlining your APIs in the interview... candidates mess up more often by spending too much time on API design than by underinvesting.”

上下文：API 设计是面试交付框架的一部分，但面试官的核心考核点通常是后续的分布式系统架构设计。控制 API 环节在 5 分钟内，切忌陷入细节无法自拔。

3. 关于原则的应用技巧： “You don't get points for listing principles in the abstract. You get points for applying them out loud. 'I'll use an idempotency key on this endpoint so a retry can't double-book the seat' lands far better than a lecture on idempotency.”

上下文：不要空谈设计原则的定义，而要在设计具体端点时将原则作为决策依据直接说出来，以此体现工程实践经验。

可操作的洞察与建议

  1. 快速定调与控制时间

    • 入手时声明：“我将使用 REST API 来定义面向用户的接口”。
    • 严格将公共 API 列举控制在 3-5 个核心端点，涵盖核心业务流程（如浏览、查询、提交创建）即可，快速过渡到 High-Level Design。

  2. 主动展示生产级思考（亮眼加分项）

    • 处理写操作：在涉及支付、预订的 POST 接口中，主动指出使用 Idempotency-Key 请求头防重试。
    • 处理读操作：在列表/集合接口中，主动加上 limit 和 offset（或 cursor）参数，并注明“设置单页上限以保护数据库”。
    • 处理安全性：简要说明“用户侧 API 使用 JWT 传递身份上下文；内部微服务通信使用 gRPC 和 API Key”。

  3. 根据角色定位调整策略

    • 通用后端/架构岗位：保持 API 设计简洁、规范，快速切入分布式系统架构。
    • 前端/产品/初级岗位：准备接受关于 API 设计的深挖（如字段设计、Presigned URL 实现细节等），需对特定端点的 JSON Request/Response 结构有更精细的描述。
